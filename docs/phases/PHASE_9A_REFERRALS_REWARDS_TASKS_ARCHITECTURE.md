# Phase 9A — Referrals, Rewards & Task Rewards: Architecture, Data Model & Implementation Plan

Status: **architecture checkpoint** — this document is a design deliverable only.
Nothing in this document is implemented. Phase 9B performs the implementation.

Scope: referrals, referral signup rewards, referral deposit rewards, general task
rewards, reward provenance, withdrawal integration, admin operations, RLS/RBAC,
ledger integration, reconciliation, Edge Functions, events, testing, and the
exact Phase 9B implementation sequence.

---

## 1. Executive Summary

**What exists today.** Phase 2 created the referral _identity_ foundation:
`profiles.referral_code` (unique, server-generated, case-normalized) and
`profiles.referred_by` (set once at signup from `raw_user_meta_data.referral_code`
inside `handle_new_user()`). Phase 3 seeded referral _policy_ keys into
`admin_config`. Phase 4 created the ledger with a dedicated `BONUS` wallet
bucket, the `REWARD_CREDIT` and `BONUS_RELEASE` journal types, and seeded
`REWARD_EXPENSE` system accounts for NGN and USD — all currently unused.
Phase 5–8 built deposits, webhooks, the outbox, withdrawals with
HOLD/EXTERNAL_PAYOUT/HOLD_RELEASE journals, KYC gating, PIN verification stamps,
and reconciliation. TypeScript contracts (`ReferralSummary`, `ReferralRecord`,
`AdminReferralRow`, `RewardGrantRow`, `ReferralOverview`) and UI surfaces
(web referrals page, admin referrals page, wallet BONUS card with a
"Transfer to available" dialog) already exist but are served by mock data.

**What Phase 9 introduces.** Two reward subsystems sharing one ledger-backed
grant model:

- **Referral rewards** — a durable `referrals` relationship row plus
  `reward_grants` for (a) the ₦1,500 signup reward (PENDING until the referred
  user deposits ≥ ₦5,000/$5 _and_ invests) and (b) the 5% deposit referral
  reward (issued on every qualifying deposit, capped at ₦10,000/$10 per event).
- **Task rewards** — `reward_tasks` + `task_requirements` + `task_claims` with a
  provider/strategy verification architecture; the first task is
  "Join RentBrown Community" (Telegram leg auto-verified via Bot API,
  WhatsApp leg manually verified — see §9.4).

**Critical conflicts found in current code** (must be fixed in 9B, not
silently preserved):

| Existing seed (0004)                                                | Phase 9 decision                            |
| ------------------------------------------------------------------- | ------------------------------------------- |
| `referral.qualifying_deposit_minor` = 5,000,000 (₦50,000), NGN only | ₦5,000 / $5 per currency                    |
| `referral.deposit_referral_bps` = 100 (1%)                          | 500 (5%)                                    |
| `referral.signup_reward_minor` = 150,000 (₦1,500), NGN only         | ₦1,500 confirmed; USD value undecided (§22) |

**Core design decisions proposed:**

1. Rewards are issued into the existing `BONUS` bucket via existing
   `REWARD_CREDIT` journals — no parallel wallet system.
2. Provenance lives in a **grant sub-ledger** (`reward_grants` counters +
   `reward_allocations` movement rows), not in extra wallet buckets. The ledger
   remains the money truth; grants answer "how much of this user's money is
   reward-origin and where is it."
3. Withdrawals and investments draw reward funds by allowing a `BONUS` leg in
   the existing `HOLD` shape (one-line relaxation of `assert_journal_shape`),
   so holds mirror-release cleanly on rejection. User-initiated
   "transfer to available" uses existing `BONUS_RELEASE`.
4. Referral-reward withdrawals are exempt from the KYC gate and the
   never-deposited rule, computed from a server-side _exempt pool_ per
   (user, currency).
5. Reward reversal/recovery uses two new journal types (`REWARD_REVERSAL`,
   `REWARD_RECOVERY`) and one new system account (`REWARD_RECEIVABLE`) so a
   reversed reward whose funds were already spent becomes auditable debt —
   never a silent negative or a blocked transaction.
6. Task verification is a per-requirement handler dispatch: server-verifiable
   kinds (Telegram `getChatMember`) run in an Edge Function; WhatsApp is manual
   admin review because no reliable official API exists for arbitrary
   community-group membership (§9.4).

## 2. Current-State Audit

### 2.1 Phase 2 — auth, profiles, referral identity (0001)

- `handle_new_user()` trigger on `auth.users` creates `profiles` rows and reads
  `raw_user_meta_data ->> 'referral_code'`, normalized with `upper()` before
  lookup. Attribution is one-shot at signup; there is no post-signup attach.
- `profiles.referral_code text not null unique`; generated by
  `generate_referral_code()` server-side. Clients cannot write either column
  (RLS + no RPC exposes them).
- `profiles_referred_by_idx` exists. **No `referrals` relationship table
  exists** — `referred_by` is a bare FK; there is no status, no timestamps of
  qualification, no uniqueness beyond the FK itself.
- Admin roles (`SUPER_ADMIN`, `FINANCE_ADMIN`, `OPERATIONS_ADMIN`, …) and
  `has_admin_role()` exist; `is_admin()` read gate used by all domain RLS.

### 2.2 Phase 3 — domain schema + config (0002–0004, 0011–0012)

- `admin_config(key text pk, value jsonb, …)` with `config_number()`,
  `config_bool()`, `config_text()` helpers; admin writes via definer RPCs,
  audited.
- Seeded referral keys (single-scalar, NGN-implicit): see conflict table in §1.
- `investments` carries `user_id`, `round_id`, `slots`, `principal_minor`,
  `status` (`ACTIVE`/`MATURED`/`SETTLED`), `payment_reference`.

### 2.3 Phase 4 — ledger (0005–0007)

- `journal_entries` (immutable) → `ledger_entries` (immutable) →
  `ledger_accounts` (USER `user:<uid>:<bucket>:<cur>` / SYSTEM
  `system:<kind>:<cur>`) → `wallets` projection (`available_minor`,
  `reserved_minor`, `bonus_minor`, `pending_minor`, CHECK ≥ 0, updated only
  inside `post_journal()` under `app.ledger_posting=1`).
- `post_journal()` is the sole financial write path: idempotent on
  `idempotency_key`, balanced, single-currency, single-user per journal,
  `FOR UPDATE` wallet locks, `assert_journal_shape()` gate enumerates every
  legal account/direction multiset per `journal_type`.
- Already-defined but **unused** shapes: `REWARD_CREDIT`
  (DR `REWARD_EXPENSE` → CR user `BONUS`) and `BONUS_RELEASE`
  (DR `BONUS` → CR `AVAILABLE`).
- `reverse_journal()` posts a full mirror `REVERSAL` (once per journal,
  enforced by unique index on `reverses_journal_id`). It cannot do _partial_
  reversal — important for reward recovery (§10.4).
- `reconcile_wallets()` compares stored vs ledger-derived balances.

### 2.4 Phase 5 — deposits, webhooks, outbox, withdrawals (0008–0011)

- `confirm_deposit()`: locks deposit `FOR UPDATE`, idempotent on status,
  posts `FUNDING_CREDIT`, transitions to `CONFIRMED`. **This is the referral
  qualification hook.**
- `refund_deposit()`: reverses the funding journal via `reverse_journal()`,
  transitions to `REFUNDED`. **This is the reward revocation hook.**
- `payment_provider_events` dedupes inbound webhooks by `idempotency_key`;
  `mark_provider_event()` tracks processing. Duplicate webhooks are already
  absorbed before `confirm_deposit` re-runs.
- `outbound_events` is the durable outbox (written in the same transaction as
  the domain fact, delivered by `outbox-worker`). Phase 9 reuses it.
- `withdrawals` holds `hold_journal_id`, `payout_journal_id`,
  `release_journal_id` — already a per-withdrawal journal chain we extend, not
  replace.

### 2.5 Phase 6 — investments (0013–0015)

- `request_investment()`: `HOLD` (AVAILABLE→RESERVED) then
  `INVESTMENT_DEBIT` (RESERVED→`INVESTMENT_PRINCIPAL_PAYABLE`), capacity
  increment + per-user limits inside one txn, `unique_violation` idempotent
  replay. **Second qualification hook** (referred user "invests" = an
  `investments` row committed `ACTIVE`).

### 2.6 Phase 7 — maturity (0016–0017)

- `MATURITY_CREDIT` pays payable(s) → user AVAILABLE. Maturity proceeds are
  _not_ reward-origin regardless of what funded the investment — they credit
  AVAILABLE with no provenance attachment (open decision §22).

### 2.7 Phase 8 — KYC, PIN, withdrawals (0018–0021)

- `request_withdrawal()` (post-0021): idempotent replay first → destination
  validation → KYC gate (`kyc.required_for_withdrawal`, first-withdrawal
  exception `< withdrawal.first_without_kyc_max_minor.<CUR>` under advisory
  lock) → PIN verification-stamp check → fee snapshot → `HOLD` → insert.
- `decide_withdrawal()` / `mark_withdrawal_paid()`: HOLD_RELEASE on
  reject/fail; `EXTERNAL_PAYOUT` (with fee split to `FEE_REVENUE`) on paid.
- Write-guard pattern: tables writable only under a transaction-local flag
  (`app.withdrawal_write`, `app.ledger_posting`) set inside definer functions —
  Phase 9 tables reuse this pattern (`app.reward_write`, `app.task_write`).
- No explicit "must have deposited" gate exists today — it was _implicit_
  (AVAILABLE could only be funded by deposits/maturity/adjustments). Phase 9
  makes the rule explicit because BONUS breaks the implicitness (§12.3).

### 2.8 UI / data-source surface

- `InvestorDataSource` seam: `getReferralSummary()`, `listReferrals()`,
  wallet reads, `requestWithdrawal()` — all mock-backed today.
- `packages/types`: `ReferralStatus`, `ReferralRewardKind`,
  `ReferralPolicy`, `RewardGrantStatus`, `AdminReferralRow`,
  `RewardGrantRow`, `ReferralOverview` already defined — Phase 9B wires real
  RPCs to these contracts rather than inventing new shapes.
- Web wallet BONUS card + "Transfer to available" dialog exist with a stub
  toast ("arrives with the backend phase") — 9B replaces the stub with
  `transfer_bonus_to_available`.
- Admin `/referrals` page consumes `useReferralOverview`/`useReferrals`/
  `useRewardGrants` hooks — mock today.
- `referrals.read`/`referrals.manage` permissions already exist on
  `OPERATIONS_ADMIN` (read+manage) and `FINANCE_ADMIN` (read only).
  **Task-management permissions do not exist** — new keys needed (§14).

| Requirement                          | Supported today?                                                                                                |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| Unique stable referral code          | ✅ `profiles.referral_code` unique, server-generated                                                            |

**Proposal:** add `referrals` as the durable reward relationship entity;
`profiles.referred_by` stays as the attribution fast-path, backfilled into
`referrals`. The referrals row is created inside `handle_new_user()` (extended)
so attribution and relationship insert remain atomic with signup.

## 4. Referral Business Rules (final, from product decisions)

1. Signup reward = **₦1,500** (admin-configurable; USD value open, §22).
   Status PENDING at referral creation.
2. Signup reward qualifies when the referred user has **both**:
   ≥1 `CONFIRMED` deposit ≥ qualifying minimum **and** ≥1 committed investment.
3. Deposit referral reward = **5% of the entire qualifying deposit** (not just
   the threshold), capped at **₦10,000 / $10 per deposit event**. Issued on
   **every** qualifying confirmed deposit — there is no first-deposit-only rule.
4. Qualifying minimum = **₦5,000 / $5**, per-currency config.
5. Referral rewards require **no KYC** and are withdrawable even with **zero
   personal deposits**.
6. Refund/reversal of a qualifying deposit revokes its deposit reward and can
   un-qualify/revoke the signup reward — via ledger-backed recovery, never a
   silent wallet subtraction.
7. Referral codes immutable; relationship immutable once created; self-referral
   rejected; suspended referrer → new rewards blocked, existing PENDING grants
   stay PENDING pending admin decision (§22).

## 5. Referral Reward Lifecycle

```
                referred deposits ≥ min        referred invests
                 + referred invests      (if deposit already qualified)
PENDING ────────────────────────────► QUALIFIED ──────────────► CREDITED
  │                                   (transient — evaluated    (REWARD_CREDIT
  │ deposit refunded / invalidated     & issued atomically)      journal posted,
  ▼                                                               bonus_minor += amt)
DISQUALIFIED
  │
  ▼ CREDITED grant later: deposit refunded → REVERSED (any unspent part)
                          unrecoverable part → reward_receivables debt
```

`reward_grants.status` aligns to the existing `RewardGrantStatus` contract:
`PENDING | QUALIFIED | CREDITED | REVERSED | BLOCKED`.

- `QUALIFIED` is observable (a `reward_events` row + grant transition) but
  short-lived: qualification and issuance happen in the same transaction, so
  the grant lands `CREDITED`. QUALIFIED persists only if issuance is deferred
  (e.g. `BLOCKED` referrer) — keeps the contract meaningful.
- Post-issue state is carried by **counters**, not status:
  `bonus_minor` (in BONUS bucket), `released_minor` (in AVAILABLE, reward-origin),
  `reserved_minor` (in a pending withdrawal/investment hold),
  `consumed_minor` (paid out or invested), `reversed_minor` (recovered).
- **Invariant (reconciled):** `issued_minor = bonus + released + reserved +
consumed + reversed` and `issued_minor = original amount`.

Deposit-reward grants skip PENDING — created `CREDITED` atomically inside
`confirm_deposit`.

## 6. General Task Reward Architecture

```
Admin defines task (+ requirements, reward, window, eligibility)
        │ publish (versioned, audited)
        ▼
Investor lists published tasks → opens task → submits claim
        │ claim_task() RPC: eligibility gates, unique-claim insert
        ▼
Claim per-requirement verification:
  SERVER_AUTO legs → Edge Function runs provider adapter → settle_task_claim()
  MANUAL legs      → evidence stored → admin review → settle_task_claim()
        │ all required legs verified
        ▼
Reward issuance: reward_grants(kind=TASK) + REWARD_CREDIT journal → BONUS
        │ same provenance/withdrawal/reversal path as referral rewards
        ▼
Done. Failure at any leg → REJECTED; expired verification → EXPIRED; retryable.
```

The frontend submits `{task_id, idempotency_key, evidence}` and never computes
rewards. Verification adapters are per-requirement-kind handlers registered in
the claim-settlement service, not per-task hardcoding.

### 7.1 `reward_tasks`

| Column                                 | Type           | Notes                                                                                           |
| -------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| `id`                                   | uuid pk        |                                                                                                 |

| `title`, `description`, `instructions` | text           | display                                                                                         |
| `cta_label`, `cta_url`                 | text           | nullable; links also live on requirement configs                                                |
| `icon`                                 | text           | token/icon name, not a URL blob                                                                 |
| `reward_amount_minor`                  | bigint > 0     | **authoritative** — never client-supplied                                                       |
| `reward_currency`                      | currency_code  |                                                                                                 |
| `claim_policy`                         | enum `ONE_TIME | REPEATABLE`                                                                                     | v1: ONE_TIME |
| `max_claims`                           | int            | null = unlimited (repeatable only)                                                              |
| `cooldown_seconds`                     | int            | null; repeatable only                                                                           |
| `status`                               | enum `DRAFT    | PUBLISHED                                                                                       | PAUSED       | ARCHIVED` | visibility gate |
| `starts_at`, `ends_at`                 | timestamptz    | schedule/expiration                                                                             |
| `eligibility`                          | jsonb          | `{requires_deposit, requires_investment, requires_kyc, account_status}` — evaluated server-side |
| `version`                              | int            | bumped on publish-after-edit                                                                    |
| `published_at`, `published_by`         |                | audit                                                                                           |
| `sort_order`                           | int            |                                                                                                 |
| `created_by`, `request_id`, timestamps |                |                                                                                                 |

**Rationale:** reward amount/currency/window/status as columns (indexed,
constrained); eligibility as jsonb (extensible rule bag evaluated by a
`task_user_eligible(task, user)` function — new rules need code anyway);
per-leg verification as a child table (relational, not jsonb) because claims
join to individual legs.

**Immutability after publish:** `reward_amount_minor`, `reward_currency`,
`claim_policy` are frozen once `PUBLISHED` — edits require PAUSE → new version.
A `reward_tasks` update trigger rejects mutation of frozen columns when
`published_at is not null` (mirrors existing immutability-trigger style).

### 7.2 `task_requirements`

`id, task_id fk, seq, kind, config jsonb, required bool, instructions text`

`kind` enum: `TELEGRAM_MEMBERSHIP | WHATSAPP_MEMBERSHIP | APP_ACTION |
EXTERNAL_WEBHOOK | MANUAL_EVIDENCE`. `config` holds provider specifics
(`chat_id`, `invite_url`, `phone_instructions`, webhook URL+secret ref) —
never secrets themselves (secret names only; values in Edge Function env).

### 7.3 `task_claims`

`id, task_id fk, user_id fk, status, idempotency_key unique, evidence jsonb,
verification_summary jsonb, reward_grant_id fk null, request_id, attempt_of uuid null,
created_at, updated_at, settled_at`

status enum: `PENDING | VERIFYING | MANUAL_REVIEW | APPROVED | REWARDED |
REJECTED | EXPIRED`.

- `unique (task_id, user_id) where status not in ('REJECTED','EXPIRED')` for
  ONE_TIME tasks → duplicate-safe + retryable after failure.
- `idempotency_key` unique → double-click/retry converge.
- Repeatable tasks (future): unique on `(task_id, user_id, attempt_no)`;
  attempt_no derived under claim lock.

### 7.4 `task_claim_legs` (per-requirement results)

`claim_id, requirement_id, status (PENDING|VERIFIED|FAILED|MANUAL_REVIEW|SKIPPED),
verified_by (SYSTEM|ADMIN), verifier_ref, evidence jsonb, note, checked_at`
unique `(claim_id, requirement_id)`.

### 7.5 `user_identities`

`user_id, provider ('telegram'|…), provider_user_id text, provider_username,
linked_at, link_token, token_expires_at` — unique `(provider, provider_user_id)`
and `(provider, user_id)`. Telegram linkage is required before the Telegram leg
can verify (deep-link `/start <token>` flow, §9.2).

### 7.6 `referrals`

`id, referrer_id fk, referred_id fk unique, status enum
(ACTIVE|DISQUALIFIED|BLOCKED), signup_reward_grant_id fk null,
attribution_source text ('signup_metadata'|…), created_at` +
unique `(referrer_id, referred_id)`, CHECK `referrer_id <> referred_id`.

### 7.7 `reward_grants`

`id, user_id, kind enum (REFERRAL_SIGNUP|REFERRAL_DEPOSIT|TASK), status,
currency, issued_minor, bonus_minor, released_minor, reserved_minor,
consumed_minor, reversed_minor, referral_id null, deposit_id null,
task_claim_id null, issue_journal_id, request_id, created_at, updated_at`

Uniqueness: `(kind, referral_id)` for signup; `(kind, deposit_id)` for deposit
rewards — _deposit-level_, so the reward attaches to whichever deposit; the
referrer is derived through `referral_id`/`deposits.user_id` (store
`referrer_id` column too for query simplicity — duplicated but reconciled);
`(kind, task_claim_id)` for tasks. Every grant carries exactly one source arm.

### 7.8 `reward_allocations`

`id, grant_id fk, movement enum (ISSUE|RELEASE|HOLD|HOLD_RETURN|CONSUME|
REVERSE|RECOVER), amount_minor, journal_id null, withdrawal_id null,
investment_id null, note, created_at` — append-only, write-guarded. This is the
audit trail that answers "why is ₦X withdrawable / where did reward funds go".

### 7.9 `reward_receivables`

`id, user_id, currency, amount_minor, outstanding_minor, source_grant_id,
reversal_journal_id, status (OPEN|SETTLED|WRITTEN_OFF), created_at, settled_at`
— debt ledger for unrecoverable reversals (§10.4).

## 8. Task Claim Model — idempotency & concurrency

- Claim insert is the single concurrency gate: partial unique index +
  `idempotency_key` unique; concurrent claims → one wins, loser gets
  `ERR_TASK_ALREADY_CLAIMED` (or the winner's row on replay).
- `claim_task()` locks the task row `FOR SHARE` (publish/update serializes
  against claims), checks status PUBLISHED + window + eligibility in txn.
- Verification is async-by-design: auto legs settle via
  `settle_task_claim()` (service-role only) which re-locks the claim row
  `FOR UPDATE`; a claim already `REWARDED`/`REJECTED` short-circuits
  idempotently.
- Timeout: claims stuck `VERIFYING` > claim_ttl (config, default 15 min) become
  `EXPIRED` via sweep (outbox-worker or pg_cron-style EF) → user may retry
  (new claim, new attempt).
- Reward issuance uniqueness is belt-and-suspenders: `reward_grants` unique on
  `(kind, task_claim_id)` makes a second issuance impossible even if settle
  races.

## 9. Verification Architecture

### 9.1 Dispatch

`settle_task_claim` iterates `task_claim_legs`: for each `SERVER_AUTO` leg it
invokes the registered adapter for `requirement.kind`; `MANUAL` legs wait for
admin. Claim settles REWARDED when all `required` legs are VERIFIED; REJECTED
on any required leg FAILED (with note). Verification outages → leg stays
PENDING → claim keeps VERIFYING until ttl → `EXPIRED`, never silent-fails.

### 9.2 Telegram — feasible ✅

- **Mechanism:** Bot API `getChatMember(chat_id, user_id)` returns member
  status (`member|administrator|creator` = pass; `left|kicked`/`not found` =
  fail). Guaranteed reliable only if the bot is an **administrator** in the
  group/channel.
- **User linkage:** Telegram users are numeric IDs we cannot derive from a
  username. Flow: `create_identity_link_token('telegram')` RPC mints a
  short-lived token → UI deep-links `t.me/<bot>?start=<token>` → new Edge
  Function `telegram-webhook` receives the `/start` message (verified via
  `X-Telegram-Bot-Api-Secret-Token`), stores `user_identities` row.
  Optionally also consume `chat_member` webhook updates for passive
  re-verification.
- **Secrets needed:** bot token + webhook secret (Edge env, never in DB/audit).
- **Admin requirement:** bot must be added to the target group/channel as admin.

### 9.3 WhatsApp — NOT reliably automatable ❌

- Meta's official Cloud API **Groups API** exists but requires Official
  Business Account status, caps groups at **8 participants**, and cannot add
  members — unusable for a community group.
- There is **no official endpoint** to check membership of an arbitrary
  WhatsApp group/community a user joined via invite link.
- Third-party gateways (Whapi.Cloud, Evolution API) can enumerate
  participants/approve join requests, but are unofficial, account-ban-risky,
  and ToS-fragile — **not recommended as the financial gate for real rewards**.
- **Recommended v1:** `WHATSAPP_MEMBERSHIP` leg → `MANUAL` verification: the
  claim stores the user's submitted WhatsApp phone number (E.164, evidence
  jsonb); an admin cross-checks the community member list in the WhatsApp admin
  app and approves/rejects via `admin_review_task_claim`. Optional screenshot
  upload (Storage, private bucket, same conventions as KYC docs) as supporting
  evidence — flag for product decision (§22).
- Alternative to consider later: an approval-required group join flow where
  joining itself creates a reviewable record — still manual.

### 9.4 First task — "Join RentBrown Community"

- Task `code='join-community'`, ONE_TIME, reward from task config (e.g. ₦500 —
  final amount is a product/admin config choice at publish, §22).
- Requirements: leg 1 `TELEGRAM_MEMBERSHIP` (auto, requires linked identity);
  leg 2 `WHATSAPP_MEMBERSHIP` (manual review). Reward settles when **both**
  legs verify — compound semantics come free from the per-leg model.
- Invite links/chat IDs live in requirement `config` (admin-editable), never in
  frontend constants.

## 10. Ledger Integration

### 10.1 New enum values / accounts

- `system_account_kind` += **`REWARD_RECEIVABLE`** (ALTER TYPE … ADD VALUE;
  seeds in a _separate_ migration since new enum values can't be used in the
  same transaction). Seeded for NGN + USD in `system_accounts`.
- `journal_type` += **`REWARD_REVERSAL`**, **`REWARD_RECOVERY`**.
- `assert_journal_shape` additions:
  - `HOLD`: `v_usr_dr <@ '{AVAILABLE,BONUS}' AND v_usr_dr <> '{}'` →
    `v_usr_cr = '{RESERVED}'` _(relaxation — lets withdrawals AND investments
    draw bonus directly; same-user rule already enforced by `v_owners ≤ 1`)_.
  - `HOLD_RELEASE`: `v_usr_dr='{RESERVED}'`, `v_usr_cr <@ '{AVAILABLE,BONUS}'`
    (mirror of the relaxed hold).
  - `REWARD_REVERSAL`: `v_sys_cr = '{REWARD_EXPENSE}'`,
    `v_usr_dr <@ '{BONUS,AVAILABLE}'`, `v_sys_dr <@ '{REWARD_RECEIVABLE}'`,
    at least one DR present. _(Partial reversal: claw back unspent reward
    buckets; remainder becomes receivable.)_
  - `REWARD_RECOVERY`: `v_sys_cr = '{REWARD_RECEIVABLE}'`,
    `v_usr_dr <@ '{BONUS,AVAILABLE}'`, `v_sys_dr='{}'`. _(Collects debt when
    the user later holds funds.)_

### 10.2 Issuance

`issue_reward(grant)`: `post_journal('REWARD_CREDIT', cur,
[DR system:reward_expense X, CR user:<u>:bonus X],
ref 'RWD-<grant>', key 'rwd:issue:<grant>', entity_type 'reward_grant')` —
idempotent by grant id; `reward_grants.bonus_minor += X` + ISSUE allocation row
in the same txn.

### 10.3 Spend paths

- **Transfer to available:** `transfer_bonus_to_available()` →
  `BONUS_RELEASE` + RELEASE allocations + grant counter move
  `bonus→released`. Existing shape, no changes.
- **Withdrawal:** HOLD journal gets a BONUS debit leg sized to the allocated
  reward portion (§12). HOLD_RELEASE mirror returns funds to the _same_
  buckets on reject/fail — provenance restored automatically.
- **Investment:** `request_investment` HOLD gains the same optional BONUS leg;
  allocated grants move `bonus/released → reserved → consumed` across
  HOLD/INVESTMENT_DEBIT with allocation rows. MATURITY_CREDIT output is
  ordinary AVAILABLE (reward provenance ends at consumption — documented,
  §22 decision).

### 10.4 Reversal / debt

`revoke_deposit_rewards(deposit)` (called by `refund_deposit` after the
funding reversal, service-only): for each affected grant compute
`remaining = issued − reversed`; take `min(remaining, bonus)` then
`min(rest, released)` then `min(rest, reserved)` _(only for still-pending
withdrawals — see §12.5; recommended: do NOT drain reserved; remainder →
receivable)_ then remainder → `REWARD_RECEIVABLE`. Posts ONE
`REWARD_REVERSAL` journal (mixed DR legs, CR `REWARD_EXPENSE` total) +
updates counters + REVERSE/RECOVER allocations + `reward_receivables` row
for the residual. This is deliberately **not** `reverse_journal()` — full
mirror reversal of a partially-consumed grant would violate wallet CHECKs.

Debt collection: every issuance path first nets outstanding receivables —
post REWARD_CREDIT for full grant, then immediately `REWARD_RECOVERY`
DR bonus `min(debt, grant)` CR `REWARD_RECEIVABLE`. Debt also collectible by
admin adjustment flows (FINANCE_ADMIN). Never blocks unrelated withdrawals
automatically — the receivable is a ledger fact + ops signal; policy on
forcing offset is config (`reward.debt_offset_on_issue=true` default).

Deposit-reward grants on a refunded deposit are reversed entirely; a PENDING
signup reward that depended on the refunded deposit reverts qualification
(grant stays PENDING unless another qualifying deposit+investment exists —
evaluator re-checks).

## 11. Reward Provenance

The provenance answer set per (user, currency):

| Question                             | Answer source                                                  |
| ------------------------------------ | -------------------------------------------------------------- |
| Earned from referrals / tasks        | Σ `issued_minor` by `kind`                                     |
| Still reward-balance                 | Σ `bonus_minor`                                                |
| Moved to main, still reward-origin   | Σ `released_minor`                                             |
| In a pending hold                    | Σ `reserved_minor`                                             |
| Spent/invested/withdrawn             | Σ `consumed_minor` (via allocations: investment vs withdrawal) |
| Reversed/recovered                   | Σ `reversed_minor` + `reward_receivables.outstanding`          |
| **Withdrawable without deposit/KYC** | Σ `bonus + released` over active grants                        |
| Deposit-origin funds                 | `available − Σ released`                                       |

"Moved to main wallet" (`BONUS_RELEASE`) does **not** lose origin —
`released_minor` keeps the accounting alive, and every movement has a
`reward_allocations` row with the journal reference. UI labels (Main /
Invested / Referral / Rewards / Available-to-withdraw) map to these computed
projections, not physical wallets.

Allocation order at spend time (deterministic, audit-friendly): **BONUS first
(FIFO by grant), then `released` rewards in AVAILABLE, then ordinary
AVAILABLE.** This maximally preserves ordinary-fund provenance and keeps the
exempt pool accurate.

## 12. Withdrawal Integration

### 12.1 Server-side "available to withdraw"

`get_withdrawal_quote()` extended to return:

```
available_minor, bonus_minor, reward_exempt_minor  (= Σ bonus+released),
ordinary_available_minor (= available − released),
requires_deposit_history bool, has_confirmed_deposit bool,
kyc_required bool, first_withdrawal bool, fee preview, min withdrawal
```

Client renders; server decides.

### 12.2 `request_withdrawal` changes (post-0021 signature kept)

Inserted **after idempotent replay & destination, before KYC gate**:

1. `exempt := Σ grants(bonus+released)` for (uid, currency) — under the
   existing advisory lock.
2. `reward_part := min(amount, exempt)`; `ordinary_part := amount − reward_part`.
3. **Deposit-history gate:** if `ordinary_part > 0` and no CONFIRMED deposit →
   `ERR_NO_DEPOSIT_HISTORY` (new; makes the previously-implicit rule explicit —
   admin-credited AVAILABLE is covered by an open decision, §22).
4. **KYC gate:** if `ordinary_part > 0` → existing KYC/first-withdrawal logic
   on the _ordinary_ portion. If `ordinary_part = 0` → skip KYC entirely
   (referral-reward exception, business rule 9/10).
5. PIN stamp check unchanged.
6. Grant allocation: FIFO over grants → HOLD journal with BONUS leg
   (`reward_part` from bonus) + AVAILABLE leg (`ordinary_part` + any released
   reward drawn); `reward_allocations` rows move `bonus/released → reserved`;
   `withdrawal_source_allocations` rows record `{withdrawal_id, grant_id|null,
source_kind, amount}`.
7. `withdrawals` gains `reward_amount_minor`, `ordinary_amount_minor`
   (denormalized snapshot for reporting; allocations table is authoritative).

### 12.3 Required-behavior matrix (spec §10)

| Case                                 | Behavior                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| No deposit, no reward                | `ERR_INSUFFICIENT_WITHDRAWABLE` (nothing held)                                      |
| No deposit, qualified reward ≤ bonus | allowed, no KYC, HOLD draws BONUS                                                   |
| Deposit + ordinary funds             | today's rules                                                                       |
| Ordinary funds, no KYC               | `ERR_KYC` (unless first-withdrawal `<` threshold)                                   |
| Mixed: reward ₦5k + ordinary ₦3k     | reward part exempt; ordinary part gated                                             |
| Reward already released to available | still exempt (released_minor pool)                                                  |
| Never deposited, ordinary part > 0   | `ERR_NO_DEPOSIT_HISTORY`                                                            |
| Concurrent withdrawals               | advisory lock serializes; exempt pool re-read per txn                               |
| Reversal while withdrawal pending    | reversal takes bonus→released; reserved NOT drained → receivable + ops flag (§12.5) |

### 12.4 Rejection / release

HOLD_RELEASE mirror returns funds to original buckets; allocations
`HOLD_RETURN` restore grant counters (`reserved→bonus` or `→released` as
recorded). Reward-origin funds that were released before the withdrawal stay
`released` (still exempt) — consistent.

### 12.5 Reversal vs pending withdrawal

Reserved reward funds are **not** auto-drained mid-payout (the money is
already promised to a payout). The reversal records the unrecoverable part as
`reward_receivables` + emits an ops outbound event; admin may also manually
reject the pending withdrawal (which frees the hold back into bonus/released,
then debt collection can proceed). Flagged as the recommended default, §22.

## 16. Reconciliation — `reconcile_rewards()` checks

1. Grant invariant: `issued = bonus+released+reserved+consumed+reversed`.
2. `bonus` totals vs ledger-derived BONUS bucket per (user,currency).
3. `released` totals ≤ AVAILABLE.
4. CREDITED grant without `issue_journal_id` / journal missing.
5. Journal `REWARD_CREDIT` without a grant (entity_type mismatch).
6. Deposit reward ≠ `min(5% × confirmed_amount, cap)` → amount mismatch.
7. Deposit reward on deposit below threshold / non-CONFIRMED.
8. Duplicate rewards per (kind, source) — constraint backstop + check.
9. Referral grant where `referrals.referred_id ≠ deposits.user_id`.
10. Withdrawal allocations Σ ≠ withdrawal amount; pending withdrawal hold vs
    grants `reserved` mismatch.
11. Receivable outstanding ≠ open `reward_receivables` Σ vs REWARD_RECEIVABLE
    account balance.
12. Task claim REWARDED without grant / grant without claim.
13. Legacy scalar referral config still divergent from per-currency keys
    (drift warning).
14. Reversed grant still holding nonzero bonus/released/reserved.

## 21. Rollback / Recovery

- No destructive changes: all new tables; existing functions replaced via
  `CREATE OR REPLACE` with additive behavior gated on new tables — rollback =
  redeploy prior function bodies (kept in git history) + leave new tables
  dormant.
- `referral.enabled=false` kill-switch disables qualification without revert.
- Reward issuance failure inside `confirm_deposit` must **not** fail the
  deposit — wrap hook in a sub-block that logs + emits `reward.eval_failed`
  outbox event for replay (evaluator is idempotent and re-runnable).
